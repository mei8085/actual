## 2. Mutator 机制深度解析（关键修正）

### 2.1 Mutator 核心代码实现

**文件**: `loot-core/src/server/mutators.ts`

```typescript
// 标记处理器为变异操作
const mutatingMethods = new WeakMap();

export function mutator<T extends HandlerFunctions>(handler: T): T {
  mutatingMethods.set(handler, true);
  return handler;
}

// 核心执行逻辑
export async function runHandler<T extends Handlers[keyof Handlers]>(
  handler: T,
  args?: Parameters<T>[0],
  { undoTag, name }: { undoTag?; name? } = {},
): Promise<ReturnType<T>> {
  if (mutatingMethods.has(handler)) {
    // Mutator 方法通过 runMutator 执行
    return runMutator(() => handler(args), { undoTag }) as Promise<
      ReturnType<T>
    >;
  }

  // 非 Mutator 方法直接执行
  const promise = handler(args);
  runningMethods.add(promise);
  void promise.then(() => {
    runningMethods.delete(promise);
  });
  return promise as Promise<ReturnType<T>>;
}

// runMutator 被 sequential 包装，确保串行执行
export const runMutator = sequential(_runMutator) as typeof _runMutator;

function _runMutator<T extends () => Promise<unknown>>(
  func: T,
  initialContext = {},
): Promise<Awaited<ReturnType<T>>> {
  currentContext = initialContext;  // 设置 Undo 上下文
  return func().finally(() => {
    currentContext = null;  // 清理上下文
  }) as Promise<Awaited<ReturnType<T>>>;
}
```

### 2.2 sequential 队列机制实现

**文件**: `loot-core/src/shared/async.ts`

```typescript
export function sequential<T extends AnyFunction>(
  fn: T,
): (...args: Parameters<T>) => Promise<Awaited<ReturnType<T>>> {
  const sequenceState: {
    running: Promise<Awaited<ReturnType<T>>> | null;
    queue: Array<{ args; resolve; reject }>;
  } = {
    running: null,
    queue: [],
  };

  function pump() {
    const next = sequenceState.queue.shift();
    if (next !== undefined) {
      run(next.args, next.resolve, next.reject);
    } else {
      sequenceState.running = null;
    }
  }

  function run(args, resolve, reject) {
    sequenceState.running = fn.apply(null, args).then(
      val => { pump(); resolve(val); },
      err => { pump(); reject(err); },
    );
  }

  return ((...args) => {
    if (!sequenceState.running) {
      return new Promise((resolve, reject) => run(args, resolve, reject));
    } else {
      return new Promise((resolve, reject) => {
        sequenceState.queue.push({ resolve, reject, args });
      });
    }
  }) as T;
}
```

### 2.3 Mutator 的真实作用：**顺序执行 + Undo 上下文**

| 特性 | 代码证据 | 说明 |
|------|----------|------|
| ✅ **顺序执行** | `runMutator = sequential(_runMutator)` | 所有标记为 mutator 的方法共享一个执行队列，串行执行，避免竞态条件 |
| ✅ **Undo 上下文** | `currentContext = initialContext` + `getMutatorContext()` | 在 mutator 执行期间设置全局上下文，供 undo 系统追踪操作记录 |
| ❌ **数据库事务回滚** | **无相关代码** | mutator 机制本身不包含任何数据库 BEGIN/COMMIT/ROLLBACK 逻辑，不等于事务回滚 |

> **关键修正**：之前报告中提到的 "Mutator 内的数据库操作具有事务一致性，失败时可回滚" 是错误的。代码证据显示 mutator 仅提供**执行顺序保证**和**Undo上下文传递**，不具备数据库事务能力。

export type Mappings = Map<string, Map<string, string>>;

// 序列化 Map → JSON 字符串
export const mappingsToString = (mapping: Mappings): string =>
  JSON.stringify(
    Object.fromEntries(
      [...mapping.entries()].map(([key, value]) => [
        key,
        Object.fromEntries(value),
      ]),
    ),
  );

// 反序列化 JSON 字符串 → Map
export const mappingsFromString = (str: string): Mappings => {
  try {
    const parsed = JSON.parse(str);
    return new Map(
      Object.entries(parsed).map(([key, value]) => [
        key,
        new Map(Object.entries(value as object)),
      ]),
    );
  } catch (e) {
    throw new Error(`Failed to parse mapping: ${String(e)}`);
  }
};
```

  const msg = event.data;  // { id: UUID, name: 'preferences/get' }

    value => {
      void dispatch(
        saveSyncedPrefs({
          prefs: { [prefName]: value },  // { 'custom-sync-mappings-acc1': JSON_STRING }
        }),
      );
    },
    [prefName, dispatch],
  );

  const pref = useSelector(state => state.prefs.synced[prefName]);
  return [pref, setPref];
}
```

## 7. 结论与设计洞察

### 7.1 关键修正总结

| 之前的错误认知 | 修正后的正确结论 | 代码证据 |
|----------------|------------------|----------|
| Mutator 提供数据库事务回滚 | ❌ Mutator 仅提供**顺序执行**和**Undo上下文传递**，不包含任何事务逻辑 | `mutators.ts` 无 BEGIN/COMMIT/ROLLBACK 代码 |
| 非 mutator 写操作 = 高风险 | ⚠️ 需**逐条分析**：每个非 mutator 写操作都有专属风险控制机制（失败清理、沙箱、锁释放等） | `budgetfiles/app.ts` 各方法 try-catch |
| 映射只有写链路 | ✅ 映射有**读写双链路**：读链路在预算加载时初始化，写链路在用户保存时触发 | `prefsSlice.ts: loadPrefs()` + `saveSyncedPrefs()` |

### 7.2 架构设计洞察

1. **Mutator 是并发控制机制，不是事务机制**
   - 解决的问题：多标签页并发写操作导致的竞态条件
   - 未解决的问题：数据库原子性、崩溃恢复

2. **SharedWorker 是架构中枢**
   - 不仅是多标签协调器，更是请求路由和回调分发的核心
   - `requestToPort` UUID 映射实现了端到端回调追踪

3. **风险控制是分层的**
   - 数据库写：Mutator 串行 + Undo 追踪
   - 文件操作：沙箱路径 + try-catch 清理
   - 生命周期：flushRunningMethods 确保状态一致性

4. **乐观更新策略**
   - saveSyncedPrefs 在请求发出后立即 dispatch(mergeSyncedPrefs)
   - 假设请求成功，失败时靠 undo 系统回滚（如果有的话）
