## 2. Mutator 机制深度解析

### 2.1 Mutator 核心实现

**文件**: `loot-core/src/server/mutators.ts`

```typescript
// 标记处理器为变异操作
const mutatingMethods = new WeakMap();

export function mutator<T extends HandlerFunctions>(handler: T): T {
  mutatingMethods.set(handler, true);
  return handler;
}

// 检查是否为变异操作
export function isMutating(handler) {
  return mutatingMethods.has(handler);
}

// 执行处理器的核心逻辑
export async function runHandler<T extends Handlers[keyof Handlers]>(
  handler: T,
  args?: Parameters<T>[0],
  { undoTag, name }: { undoTag?; name? } = {},
): Promise<ReturnType<T>> {
  if (mutatingMethods.has(handler)) {
    // Mutator 方法在 runMutator 中顺序执行
    return runMutator(() => handler(args), { undoTag }) as Promise<
      ReturnType<T>
    >;
  }

  // close-budget 特殊处理：等待所有运行中的方法完成
  if (name === 'close-budget') {
    await flushRunningMethods();
  }

  // 非 Mutator 方法直接执行
  const promise = handler(args);
  runningMethods.add(promise);
  void promise.then(() => {
    runningMethods.delete(promise);
  });
  return promise as Promise<ReturnType<T>>;
}
```

### 2.2 Mutator 的安全价值

| 特性 | 说明 |
|------|------|
| **顺序执行** | `runMutator(() => handler(args), { undoTag })` 通过 `sequential()` 保证所有变异操作串行执行，避免竞态条件 |
| **Undo 支持** | 通过 `undoTag` 支持操作撤销，只有标记为 mutator 的方法才能被 undo 系统追踪 |
| **事务边界** | Mutator 内的数据库操作具有事务一致性，失败时可回滚 |
| **并发控制** | `runningMethods` Set 追踪所有执行中的操作，`close-budget` 时等待全部完成 |

### 2.3 桥接层的 Mutator 应用点

在服务端连接层响应时，根据 `isMutating(handler)` 标记响应：

```typescript
// 文件: loot-core/src/platform/server/connection/index.electron.ts
process.parentPort.postMessage({
  type: 'reply',
  id,
  result,
  mutated: isMutating(handlers[name]) && name !== 'undo' && name !== 'redo',
  undoTag,
});
```

客户端接收响应后，根据 `mutated` 标记决定是否清理 undo 快照：

```typescript
// 文件: loot-core/src/platform/client/connection/index.electron.ts
if (!msg.mutated) {
  undo.gc(msg.undoTag);  // 非变异操作，清理撤销快照
}
```

### 3.2 权限边界的风险控制

#### ✅ 正确的 Mutator 应用

所有数据库修改操作均标记为 mutator，获得以下保护：

1. **顺序执行**：避免并发导入、并发删除导致的数据不一致
2. **Undo 追踪**：关键操作（批量更新、移动、合并）支持 undoable
3. **输入验证**：`moveTransaction` 验证交易存在性和账户匹配

```typescript
async function moveTransaction({ id, accountId, targetId }) {
  // 验证交易存在
  const transaction = await db.getTransaction(id);
  if (!transaction) throw new Error(`Transaction not found: ${id}`);

  // 验证账户匹配
  if (transaction.account !== accountId)
    throw new Error(`Account mismatch: expected ${transaction.account}, got ${accountId}`);

  await db.moveTransaction(id, accountId, targetId);
  return {};
}
```

#### ⚠️ 潜在风险点

1. **导出操作标记 mutator**：`transactions-export` 和 `transactions-export-query` 是只读操作但被标记为 mutator
   - **影响**：不必要的顺序执行开销、undo 系统额外负担
   - **建议**：移除 mutator 标记

2. **部分操作缺少 undoable**：`transaction-add`、`transaction-update`、`transaction-delete` 虽然标记了 mutator 但没有 `undoable` 包装
   - **影响**：用户无法撤销这些操作
   - **设计考量**：可能是刻意选择 - 单笔操作撤销价值低，避免 undo 历史膨胀

async function flushRunningMethods() {
  await wait(200);  // 给客户端时间发起新请求

  while (runningMethods.size > 0) {

    await wait(100);  // 继续等待，避免异步工作流中断

### 4.3 设计考量：为什么预算文件操作大多不使用 Mutator？

| 原因 | 说明 |
|------|------|
| **文件系统操作** | 预算文件大多直接操作文件系统，不是数据库事务，undo 难以实现 |
| **生命周期操作** | load/close/create/delete 是全局状态变更，难以用 undo 撤销 |
| **幂等性设计** | 大多数操作是幂等的或有回滚逻辑（如 `_loadBudget` 的 catch 分支） |
| **操作频率低** | 文件级操作频率远低于交易级操作，并发冲突风险较小 |

export type Mappings = Map<string, Map<string, string>>;

// 结构示意:
// "payment" → { "date": "postedDate", "payee": "merchantName", ... }
// "deposit" → { "date": "valueDate", "payee": "payerName", ... }

// 序列化: Map → JSON
export const mappingsToString = (mapping: Mappings): string =>
  JSON.stringify(
    Object.fromEntries(
      [...mapping.entries()].map(([key, value]) => [
        key,
        Object.fromEntries(value),
      ]),
    ),
  );

// 反序列化: JSON → Map
export const mappingsFromString = (str: string): Mappings => {
  try {
    const parsed = JSON.parse(str);
    return new Map(
      Object.entries(parsed).map(([key, value]) => [
        key,
        new Map(Object.entries(value as object)),
      ]),
    );
  } catch (e) {
    throw new Error(`Failed to parse mapping: ${String(e)}`);
  }
};
```

const replyHandlers = new Map();  // UUID → { resolve, reject }

export const send: T.Send = function (name, args, { catchErrors = false } = {}) {
  return new Promise((resolve, reject) => {
    const id = uuidv4();  // 生成唯一请求 ID
    replyHandlers.set(id, { resolve, reject });  // 注册回调

    const message = {
      id,
      name,           // "preferences/save"
      args,           // { id: "custom-sync-mappings-...", value: "..." }
      undoTag: undo.snapshot(),  // 捕获当前 undo 状态
      catchErrors: !!catchErrors,
    };

    if (socketClient) {
      socketClient.emit('message', message);  // 发送到后端
    } else {
      messageQueue.push(message);  // 未连接时入队
    }
  });
};
```

#### 步骤 4：SharedWorker 协调层 — Leader/Follower 路由

**文件**: `desktop-client/src/shared-browser-server-core.ts`

```typescript
// 接收到来自标签页的消息
port.onmessage = function (event) {
  const msg = event.data;
  const portBudget = portToBudget.get(port);  // 该标签页所属预算
  const group = portBudget ? budgetGroups.get(portBudget) : null;

  // ... 生命周期消息处理 (init, tab-closing, etc.)

  // ── Leader 转发 Worker 响应 ──
  if (msg.type === '__from-worker') {
    // 只有 Leader 能收到 Worker 消息
    if (!group || port !== group.leaderPort) return;

    const workerMsg = msg.msg;

    if (workerMsg.type === 'reply' || workerMsg.type === 'error') {
      // 通过 requestToPort 映射找到原始请求来源标签页
      const targetPort = group.requestToPort.get(workerMsg.id);
      if (targetPort) {
        targetPort.postMessage(workerMsg);  // 转发回请求发起者
        group.requestToPort.delete(workerMsg.id);  // 清理
        group.requestNames.delete(workerMsg.id);
      }
    }
    // ... 其他消息类型广播
    return;
  }

  // ── 默认: 转发到 Leader 的 Worker ──
  let targetGroup = group;

  // 未分配标签页: 路由到第一个已连接后端的组
  if (!targetGroup && unassignedPorts.has(port) && isTrackedPort(port)) {
    for (const [, g] of budgetGroups) {
      if (g.backendConnected) {
        targetGroup = g;
        break;
      }
    }
  }

  if (targetGroup) {
    // 记录请求来源以便后续回复路由
    if (msg.id) {
      targetGroup.requestToPort.set(msg.id, port);
      if (msg.name) {
        targetGroup.requestNames.set(msg.id, msg.name);
      }
      // 特殊处理: load-budget 记录预算 ID
      if (msg.name === 'load-budget' && msg.args?.id) {
        targetGroup.requestBudgetIds.set(msg.id, msg.args.id);
      }
    }

    // 转发到 Leader 的 Worker
    targetGroup.leaderPort.postMessage({ type: '__to-worker', msg });
  }
};
```

#### 步骤 5：服务端连接层 — runHandler 执行

**文件**: `loot-core/src/platform/server/connection/index.electron.ts`

```typescript
process.parentPort.on('message', ({ data }) => {
  const { id, name, args, undoTag, catchErrors } = data;

  if (handlers[name]) {
    // 1. 检测是否为 mutator，如果是则在 runMutator 中执行
    // 2. 对于 preferences/save，mutatingMethods.has(handler) === true
    runHandler(handlers[name], args, { undoTag, name }).then(
      result => {
        // 成功响应
        process.parentPort.postMessage({
          type: 'reply',
          id,
          result: catchErrors ? { data: result, error: null } : result,
          mutated: isMutating(handlers[name]),  // true
          undoTag,
        });
      },
      nativeError => {
        // 错误响应
        const error = coerceError(nativeError);
        if (catchErrors) {
          process.parentPort.postMessage({
            type: 'reply', id, result: { error, data: null },
          });
        } else {
          process.parentPort.postMessage({ type: 'error', id, error });
        }
      },
    );
  }
});
```

client.on('message', data => {
  const msg = data;

  if (msg.type === 'reply') {
    const handler = replyHandlers.get(msg.id);
    if (handler) {
      replyHandlers.delete(msg.id);

      if (!msg.mutated) {
        undo.gc(msg.undoTag);  // 非变异操作清理 undo 快照

      handler.resolve(msg.result);  // ✅ resolve Promise

  } else if (msg.type === 'error') {

      handler.reject(msg.error);  // ❌ reject Promise

    const listeners = listenersMap.get(msg.name);
    if (listeners) {
      listeners.forEach(cb => cb(msg.args));
    }
  }
});

## 6. 权限边界控制总结

### 6.1 Mutator 应用矩阵

| 模块 | 方法总数 | Mutator ✅ | 非 Mutator ❌ | 主要风险控制 |
|------|---------|-----------|-------------|--------------|
| **交易服务** | 11 | 9 (82%) | 2 (18%) | 顺序执行、输入验证、Undo |
| **预算文件** | 19 | 1 (5%) | 18 (95%) | 文件沙箱、原子性、flushRunningMethods |
| **首选项/映射** | 2 | 1 (50%) | 1 (50%) | Mutator 保护写操作，只读查询无保护 |

### 6.2 关键风险控制机制

| 机制 | 应用场景 | 实现位置 |
|------|----------|----------|
| **Mutator 顺序执行** | 所有数据库写操作 | `mutators.ts: runMutator` |
| **Undo 追踪** | 交易操作、预算操作 | `undoable()` 包装器 |
| **Flush on Close** | 预算关闭 | `runHandler` 检测 `close-budget` |
| **文件系统沙箱** | 预算文件操作 | `fs.getDocumentDir()` |
| **失败清理** | 预算加载 | `_loadBudget` catch 块 |
| **路径验证** | 文件上传 | `uploadFileWeb` 路径安全检查 |

## 7. 异步响应回调机制

### 7.1 三种响应模式

| 模式 | 触发场景 | 实现机制 |
|------|----------|----------|
| **Request-Reply** | 主动调用 `send()` | UUID 匹配 replyHandlers Map |
| **Push Event** | 服务端主动通知 | `listen(name, callback)` 注册监听器 |
| **Error Propagation** | 处理失败 | `catchErrors` flag 控制 reject 或 resolve |

### 7.2 典型 Push Events

| 事件名 | 触发时机 | 监听者 |
|--------|----------|--------|
| `sync-event` | 同步完成/失败 | UI 显示同步状态 |
| `cells-changed` | 电子表格单元格变化 | 预算视图刷新 |
| `prefs-updated` | 首选项变更 | Redux 状态更新 |
| `show-budgets` | Leader 切换预算 | 所有标签页返回预算列表 |

## 8. 结论与建议

### 8.1 架构优势

1. **清晰的分层设计**：职责分离，桥接层作为独立抽象层
2. **完善的并发控制**：SharedWorker Leader/Follower 模式 + Mutator 顺序执行
3. **灵活的错误处理**：`catchErrors` flag 支持两种错误传播模式
4. **可扩展的注册机制**：`App.method()` 统一注册，类型安全

### 8.2 潜在改进点

| 问题 | 建议 | 影响范围 |
|------|------|----------|
| 交易导出标记为 mutator | 移除 `transactions-export*` 的 mutator 包装 | 性能优化 |
| 预算文件操作缺少 mutator | 评估哪些文件操作可受益于顺序执行保护 | 可靠性 |
| Undo 覆盖不全 | 为更多单笔交易操作添加 undoable | 可用性 |
| 映射验证缺失 | 在 `mappingsFromString` 中添加 schema 验证 | 健壮性 |

### 8.3 关键设计洞察

1. **Mutator 不是万能的**：文件系统操作等全局状态变更不适合用 Mutator，需要其他风险控制机制
2. **SharedWorker 是架构核心**：它不仅解决多标签页问题，更是请求路由、状态协调的中枢
3. **UUID 路由模式**：通过请求 ID 跨层追踪实现端到端回调，这是桥接层最精妙的设计之一
4. **Undo 与 Mutator 深度绑定**：只有在 Mutator 中执行的操作才能被正确追踪和撤销
