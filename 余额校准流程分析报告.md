# Actual Budget 余额校准流程分析报告

## 概述

Actual Budget 的余额校准（Balance Reconciliation）涉及**导入层**到**同步层**的多阶段处理流程。系统通过银行同步（Bank Sync）从外部金融机构获取交易数据，与本地存储的账户余额进行比对，当存在差异时通过多阶段匹配算法进行校准，并将变更通过 CRDT 同步机制传播到其他设备。

## 三、匹配层（Matching Layer）

### 3.1 匹配策略概览

交易匹配发生在 [matchTransactions](file:///d:/fz/0508-1/solo-dogfeeding/code/120-actual/packages/loot-core/src/server/accounts/sync.ts#L698-L897) 函数中，采用**三级匹配策略**：

```
┌─────────────────────────────────────────────────────────────────┐
│                     交易匹配流程                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  第1阶段：imported_id 精确匹配                                   │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  SELECT * FROM v_transactions                            │   │
│  │  WHERE imported_id = ? AND account = ?                    │   │
│  └─────────────────────────────────────────────────────────┘   │
│                              │                                  │
│                              ▼ (未匹配)                         │
│  第2阶段：模糊匹配 - 支付方匹配                                   │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  查找条件：                                               │   │
│  │  - 日期在 ±7 天范围内                                     │   │
│  │  - 金额相同                                               │   │
│  │  - payee ID 相同                                          │   │
│  └─────────────────────────────────────────────────────────┘   │
│                              │                                  │
│                              ▼ (未匹配)                         │
│  第3阶段：模糊匹配 - 时间最近优先                                 │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  从候选集中选择：                                          │   │
│  │  - 日期最接近的交易                                       │   │
│  │  - 排除已被之前阶段匹配的交易                              │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 核心匹配逻辑

**imported_id 精确匹配**（最高优先级）：
```typescript
// accounts/sync.ts#L746-L758
if (trans.imported_id) {
  const table = reimportDeleted
    ? 'v_transactions'           // 包含已删除（墓碑）交易
    : 'v_transactions_internal'; // 仅内部可见交易
  match = await db.first<db.DbTransaction>(
    `SELECT * FROM ${table} WHERE imported_id = ? AND account = ?`,
    [trans.imported_id, acctId],
  );
}
```

**模糊匹配范围**：
```typescript
// accounts/sync.ts#L766-L767
const sevenDaysBefore = db.toDateRepr(monthUtils.subDays(trans.date, 7));
const sevenDaysAfter = db.toDateRepr(monthUtils.addDays(trans.date, 7));
```

**strictIdChecking 行为**：
- `true`：仅当导入交易**没有** `imported_id` 时才执行模糊匹配
- `false`：无论导入交易是否有 `imported_id` 都执行模糊匹配

### 3.3 匹配优先级与冲突解决

当多个导入交易可能匹配同一个本地交易时：

```typescript
// accounts/sync.ts#L716
const hasMatched = new Set(); // 追踪已被匹配的交易ID
```

- 匹配按顺序进行，后续导入交易不能匹配已匹配的本地交易
- fuzzyDataset 按日期距离排序（最近的优先）
- 通过 `hasMatched` 集合确保每个本地交易最多被匹配一次

## 四、校准层（Reconciliation Layer）

### 4.1 校准执行入口

[reconcileTransactions](file:///d:/fz/0508-1/solo-dogfeeding/code/120-actual/packages/loot-core/src/server/accounts/sync.ts#L538-L696) 是核心校准函数：

```typescript
export async function reconcileTransactions(
  acctId,
  transactions,
  isBankSyncAccount = false,
  strictIdChecking = true,
  isPreview = false,
  defaultCleared = true,
  updateDates = false,
  reimportDeleted?: boolean,
): Promise<ReconcileTransactionsResult>
```

### 4.2 差异处理策略

| 场景 | 处理方式 |
|------|----------|
| **匹配成功 + 已调节（reconciled）** | 跳过更新，记录为 `ignored: true` |
| **匹配成功 + 字段有变化** | 更新非锁定字段，保留本地覆盖值 |
| **匹配成功 + 子交易** | 级联更新子交易的 `cleared` 和 `date` |
| **未匹配 + 是墓碑（已删除）** | 预览模式显示删除预览 |
| **未匹配 + 新交易** | 创建新交易，使用 `defaultCleared` |

### 4.3 字段合并策略

对于已匹配的交易，系统采用**本地优先**策略：

```typescript
// accounts/sync.ts#L584-L594
const updates = {
  imported_id: trans.imported_id || null,
  payee: existing.payee || trans.payee || null,        // 本地 > 导入
  category: existing.category || trans.category || null,// 本地 > 导入
  imported_payee: trans.imported_payee || null,
  notes: existing.notes || trans.notes || null,
  cleared: existing.cleared || trans.cleared || false,  // 本地 > 导入
  raw_synced_data: existing.raw_synced_data ?? trans.raw_synced_data ?? null,
};
```

## 五、同步层（Sync Layer）角色

### 5.1 同步模式管理

[sync/index.ts](file:///d:/fz/0508-1/solo-dogfeeding/code/120-actual/packages/loot-core/src/server/sync/index.ts) 定义了四种同步模式：

```typescript
// sync/index.ts#L42
type SyncingMode = 'enabled' | 'offline' | 'disabled' | 'import';
```

| 模式 | 说明 |
|------|------|
| `enabled` | 完整 CRDT 同步，支持多设备 |
| `offline` | 本地离线模式，变更暂存 |
| `disabled` | 完全禁用同步 |
| `import` | **导入专用模式** - 快速路径，不经过完整同步 |

### 5.2 导入模式优化

当批量导入交易时，系统切换到 `import` 模式以提升性能：

```typescript
// sync/index.ts#L225-L250
function applyMessagesForImport(messages: Message[]): void {
  db.transaction(() => {
    for (const msg of messages) {
      if (!msg.old) {
        try {
          apply(msg);           // 直接应用，不经过 CRDT 验证
        } catch {
          apply(msg, true);     // 如果失败，尝试作为更新处理
        }
      }
    }
  });
}
```

**重要约束**：导入模式下不触发同步监听器，依赖投影状态的功能（如规则引擎）不会被执行。

### 5.3 消息批处理机制

[batchMessages](file:///d:/fz/0508-1/solo-dogfeeding/code/120-actual/packages/loot-core/src/server/sync/index.ts#L501-L524) 确保交易变更以原子批次处理：

```typescript
// 交易插入/更新流程
await batchMessages(async () => {
  // 1. 创建新交易
  addedIds = await Promise.all(
    added.map(async t => db.insertTransaction(t))
  );

  // 2. 更新已匹配交易
  await Promise.all(
    updated.map(async t => db.updateTransaction(t))
  );

  // 3. 删除交易
  await Promise.all(
    deletedIds.map(async id => db.deleteTransaction({ id }))
  );
});
// 批量结束后自动触发同步
```

### 6.2 差异发现与校准

```
银行提供数据:
  - 账户余额: $1,000
  - 交易: [TxA: -$50, TxB: -$30]

本地数据:
  - 账户余额: $950
  - 交易: [TxA: -$50]  (缺少 TxB)

差异发现:
  本地计算余额 = $950
  银行报告余额 = $1,000
  差异 = +$50 (= TxB 的金额)

校准执行:
  1. reconcileTransactions() 处理 TxB
  2. matchTransactions() 无法匹配（本地无此交易）
  3. 创建新交易 TxB: amount=-$30
  4. 本地余额更新为 $920

注意: 如果差异不是因为缺少交易，而是因为金额不匹配，
      系统不会自动修改金额，而是保留本地值。
```

## 八、总结

### 8.1 核心设计原则

1. **本地优先**：已调节（reconciled）的交易不会被自动覆盖
2. **精确匹配优先**：imported_id 精确匹配优于模糊匹配
3. **原子性保证**：通过 batchMessages 确保批量操作原子性
4. **CRDT 最终一致性**：通过 Merkle Trie 实现多设备同步
5. **增量同步**：仅同步变更，避免全量数据传输

### 8.2 同步层职责

| 职责 | 实现位置 |
|------|----------|
| 消息批处理 | `batchMessages()` |
| CRDT 验证 | `compareMessages()` |
| 状态同步 | `applyMessages()` |
| 冲突解决 | Merkle Trie 哈希比较 |
| 变更通知 | `_syncListeners` + `triggerBudgetChanges()` |

### 8.3 校准层职责

| 职责 | 实现位置 |
|------|----------|
| 交易匹配 | `matchTransactions()` |
| 差异处理 | `reconcileTransactions()` |
| 规则应用 | `runRules()` |
| 转账关联 | `transfer.onInsert/update/delete()` |
